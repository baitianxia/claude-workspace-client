# 网页信息推送自动化技术设计

状态：当前规范。本文是自动化子系统架构、状态机和可靠性边界的唯一技术所有者文档；README 只负责用户操作说明。实现变更如果影响这里定义的行为，必须在同一变更中更新本文。

## 范围与责任边界

自动化子系统是 Electron 主进程内的本地编排器，不是常驻服务器。职责固定为：

- 保存任务和最近 500 条运行记录；
- 按电脑本地时区解释五字段 Cron；
- 保证同一任务最多一个 Agent 执行；
- 启动受限的 Claude Code CLI 并验证结构化结果；
- 维护企业微信投递 Outbox 和群聊任务路由；
- 在退出、崩溃恢复和人工重试时保留明确状态。

网页抓取、页面登录、邮件组装和邮件发送都属于任务允许的 MCP 服务器。客户端不得新增自有爬虫、SMTP 凭据或隐式外部 API 调用。当前版本不引入服务端调度、PostgreSQL、Redis、多客户端协调或多机器人凭据。

## 数据与组件

- `AutomationStore` 独占 Electron 用户数据目录中的 `automation.json`，使用临时文件加原子重命名串行落盘。它不与 `workspace.json` 共用 schema。除任务和最近 500 条运行记录外，它还保存最近出现的 200 个企业微信群及本机别名；旧的 version 1 文件没有该字段时按空列表读取。
- `ScheduledJobService` 每 15 秒检查一次当前分钟。睡眠恢复只扫描最近 60 分钟，并且每个任务只选择最近一个匹配分钟。
- `AutomationService` 是任务、运行、并发、恢复、群聊路由和 Outbox 的唯一业务入口。
- `ClaudeCodeJobRunner` 解析工程内 MCP JSON，生成仅含允许服务器的临时配置，并启动一个无交互 Claude Code 子进程。
- `WeComBridge` 是单一企业微信长连接网关，同时承载交互式终端回复和所有自动化任务；业务层不能自行再创建机器人连接。

自动化配置界面必须显示这一个共享机器人的 Bot ID、连接状态和全局配置入口，不能让任务看起来拥有独立机器人凭据。机器人设置覆盖在自动化界面之上时必须保留尚未保存的任务草稿；当前版本不提供按任务选择不同机器人的能力。

工程移除前，IPC 层必须先禁用关联任务。任务记录继续保留，运行历史删除任务后也继续保留。

## 调度与并发契约

Cron 固定为 `分 时 日 月 星期` 五个字段，支持数字、列表、范围和步长；星期日接受 `0` 或 `7`。当“日”和“星期”同时受限时采用传统 Cron 的 OR 语义。

任务在写入运行记录前必须先占用按任务 ID 的运行槽，避免同时到达的手动、定时和企业微信请求越过并发检查。运行槽在最终结果落盘前不得释放。若计划分钟已存在运行记录，不得重复登记；若任务正在运行，则新增一条 `skipped` 计划记录。

客户端重启只评估启动所在的当前分钟，不补跑停机期间的计划。这个约束用于避免应用恢复时集中读取网页或重复发信。

## Agent 执行契约

每次运行启动独立 Claude Code CLI，工作目录是任务关联工程。参数必须包含：

- `--print`、JSON 输出和 JSON Schema；
- `--strict-mcp-config`，且 `--mcp-config` 指向本次过滤后的临时文件；
- 空的内置工具集合，只通过 `--allowedTools` 批准 `mcp__<server>__*`；
- `dontAsk` 权限模式、最大轮数、超时、禁用 Chrome 和禁用会话持久化。

不使用 `--bare`，因为该模式会绕开普通登录和钥匙串上下文。代价是普通用户级 Claude Code 配置仍可能参与启动；因此任务只能关联可信工程和可信 MCP 配置。项目内 MCP 路径必须是相对 JSON 路径，解析真实路径后仍在真实工程根目录内，并且是最多 2 MB 的普通文件。临时配置只复制明确允许的 `mcpServers` 项，运行结束删除，应用启动时清空专用 runtime 目录。

进程 stdout 与 stderr 合计最多 2 MB；超限、超时或用户取消都会终止进程。最终结果必须通过 schema 和主进程的第二次校验：证据仅允许 HTTP(S)，邮件状态与收件人必须一致，报告的每个收件人必须属于任务固定白名单。诊断信息截断为 8,000 字符，并对常见凭据键做尽力隐藏。

这些校验发生在 MCP 调用之后，不能撤销外部副作用。因此邮件 MCP 必须在服务端独立执行收件人白名单，并以运行 ID 作为幂等键。提示词约束和结果校验都不是授权边界。

## 运行与恢复状态机

Agent 状态流为：

```text
queued -> running -> succeeded | failed | timed-out | cancelled
scheduled overlap -> skipped
```

应用启动时，遗留的 `queued` 或 `running` 一律转成 `failed`，原因标记为结果未知，且不得自动重跑。人工只可以重试 `failed`、`timed-out` 或 `cancelled`；重试复用原运行 ID、报告码和幂等键，并增加 attempt。若该运行已有成功企业微信投递，则禁止重新运行 Agent。

成功结果为 `no-change` 时，定时和手动运行不创建普通群广播；企业微信群发起的后续请求仍必须回复原群。失败结果的待投递项标记为跳过。

## 企业微信路由与投递

群聊路由必须同时满足任务已启用、群 `chatid` 在任务目标中、发送者 `userid` 在任务白名单中。`*` 是显式的全员授权，空列表表示无人可触发。

任何具有合法 `chatid` 和发送者 `userid`、且到达业务路由的群消息，都必须先更新已发现群记录，再执行命令、去重和授权判断。新群立即落盘；已有群的最近出现时间最多每分钟落盘一次，避免高频群消息反复重写整个存储。群发现记录只用于客户端选择器，不参与授权，也不能使未配置到任务的群获得调用能力。企业微信智能机器人入站消息不提供可信群名称，客户端只能保存用户设置的本机别名；列表按最近出现时间排序，超过 200 个时淘汰最久未出现的记录。

路由优先级为：

1. 消息或引用中的 `[RPT-XXXXXXXXXX]`，且报告确实曾面向当前群建立投递项；
2. `/run 任务名称` 或唯一任务 ID 前缀；
3. 当前群和用户仅有一个可用任务时直接选中。

未知或已淘汰的报告码必须拒绝，不能静默退化到默认任务。`/chatid` 记录并返回当前群 ID，但不触发任务。企业微信 `msgid` 会随运行记录持久化去重，进程内网关还维护有限的即时去重集合。

每条报告使用稳定的 10 位十六进制报告码。WeCom 投递状态流为：

```text
pending -> sending -> sent
                   -> failed -> sending（最多 5 次）
                   -> failed（停止重试）
```

失败使用指数退避，每个目标包含首次发送在内最多尝试 5 次。进程在 `sending` 后、`sent` 落盘前退出时，恢复状态是“失败且结果未知”，随后重试可能产生重复消息。这是有稳定报告码辅助去重的至少一次投递，不得描述为严格 exactly-once。

## 关闭与验证

应用退出必须先停止调度和新群聊路由，取消所有后台 Claude Code 进程，等待已登记的状态写入结束，再断开企业微信与终端。若进程被操作系统强杀，则依赖下次启动恢复未知状态。

改动本子系统至少运行：

```text
tsc -p tsconfig.main.json --noEmit
tsc -p tsconfig.renderer.json --noEmit
tsc -p tsconfig.test.json --noEmit
vitest run
vite build
```

测试必须覆盖 Cron 边界、原子存储与中断恢复、MCP 路径和服务器过滤、CLI 参数与结构化输出、同任务并发、企业微信群发现、授权和去重、Outbox 重试以及共享机器人网关。
