# 私人助理 Agent 技术设计

状态：当前规范。本文是私人助理身份、会话、渠道路由、执行权限和客户端聊天体验的唯一技术所有者文档；README 只负责用户操作说明。实现变更如果影响这里定义的行为，必须在同一变更中更新本文。

## 产品边界

私人助理 Agent 是独立于渠道的主体。每个助理拥有自己的名称、指令、工程上下文、MCP 权限和连续会话；桌面客户端是第一入口，企业微信智能机器人只是可选的远程入口。不得把助理身份等同于企业微信 Bot 凭据。

Claude Code 管理机器人继续只处理交互式终端的权限确认、提问和完成通知，不得承载私人助理对话。现有自动化任务可以使用同一组企业微信业务 Bot 做主动推送，但自动化任务也不拥有私人助理会话。

首版私人助理只通过显式允许的 MCP 服务使用工具，不开放 Claude Code 内置 Shell、文件读写或 Chrome。应用不是 Claude Code 或模型服务的代理；每一轮仍由本机已登录的 Claude Code CLI 执行。

## 身份、入口与会话归属

`AssistantProfile` 是助理身份，最多保存 20 个。每个身份包含：

- 本机名称、启用状态和助理指令；
- 一个运行工程及工程内 MCP JSON 路径；
- 仅供主人会话使用的 MCP 服务器、超时和最大轮数；
- 主人的企业微信 `userid`；
- 可选的企业微信业务 Bot 配置 ID；

一个助理最多绑定一个企业微信业务 Bot，一个业务 Bot 同时最多绑定一个助理，避免入站消息出现身份歧义。没有绑定 Bot 的助理仍可在桌面客户端完整使用。删除仍被助理绑定的 Bot 必须失败；应先解除绑定或删除助理。

首版采用单主人模式，会话按主人身份归属，而不是简单按渠道隔离：

- 桌面客户端对话天然代表助理主人，使用该助理唯一的 `owner` 会话；
- 来自助理配置中主人 `userid` 的企业微信单聊也进入同一个 `owner` 会话，因此桌面与主人手机可以无缝续聊；
- 其他用户的企业微信单聊被静默丢弃，不回复、不启动 Agent、不创建会话；
- 企业微信群只保留显式自动化命令和群发现，不承载私人助理对话，即使消息由主人发送也不会把私人上下文回复到群里。

不得为了“上下文连续”把主人私聊记忆复制到群聊或其他用户会话。未来如需服务其他用户或支持群内助理，只能先增加明确的数据分类、授权、撤销和审计模型，不得直接复用主人会话。

只有桌面客户端和匹配 `ownerWeComUserId` 的企业微信单聊属于 `owner` 会话，并能获得助理配置的个人 MCP 工具、私有指令、工程上下文和历史。其他入站消息根本不启动 Claude Code，因此即使用户在文本中自称主人或要求读取邮箱，也没有接触主人数据的执行路径。发送者身份只信任企业微信事件的 `from.userid`，不能从消息正文推断。桌面入口默认代表当前操作系统用户；保护已解锁电脑属于操作系统账户安全边界。

## 数据与组件

- `AssistantStore` 独占 Electron 用户数据目录中的 `assistant.json`，使用临时文件加原子重命名串行落盘。它保存最多 20 个助理、每个助理唯一的主人会话和全局最近 500 个对话轮次。首版 schema 不接受其他用户或群聊会话记录。
- `AssistantService` 是助理配置、身份解析、会话队列、恢复、命令和状态事件的唯一业务入口。
- `ClaudeCodeAssistantRunner` 为每一轮启动一个无界面 Claude Code CLI，并在同一会话后续轮次使用持久化的 Claude `session_id` 恢复上下文。
- `AutomationWeComBotManager` 仍负责企业微信业务 Bot 的凭据、连接和收发，但不决定消息属于哪个助理或自动化任务。
- Electron IPC 只暴露结构化的助理配置、发送消息、重置会话和取消当前轮次操作；渲染进程不能直接启动 Claude Code 或读取磁盘配置，Claude `session_id` 也只留在主进程存储中。

助理 Secret 不新增副本。企业微信 Bot ID 和加密 Secret 继续由自动化存储与 Bot 管理器保存；`assistant.json` 只保存不含凭据的 Bot 配置 ID。对话记录可能包含用户输入和模型回复，因此 README 必须说明本机保存范围。

## 会话与轮次状态机

每个助理的主人会话同一时刻最多执行一轮，新消息按到达顺序排队。不同助理可以并行，防止一个慢请求阻塞其他助理。

轮次状态流为：

```text
queued -> running -> succeeded | failed | timed-out | cancelled
```

桌面发送成功后立即显示用户消息和运行状态，最终结果通过助理状态事件更新。企业微信收到主人的单聊消息后先用引用回复确认已入队，执行完成后再主动发送最终 Markdown 给主人。

应用启动时，遗留的 `queued` 或 `running` 轮次一律转为 `failed`，并清除对应会话的 Claude `session_id`。这是安全失败：崩溃时无法证明本地 Claude 会话是否已写入完整一轮，继续恢复可能导致客户端记录与 Claude 上下文不一致。不得自动重跑遗留轮次。

任何已经启动但未成功完成的轮次（失败、超时或取消）也必须清除当前 `session_id`，下一条消息从新上下文开始，避免把 Claude 侧可能存在的半轮记录与客户端队列重复拼接。

轮次终态和对应 `session_id` 的写入或清除必须在同一次 `assistant.json` 原子持久化中完成，不能先写失败状态再单独清会话。新消息入队时也要在同一次写入中固化消息与“曾有对话”标记，确保进程在任意两次落盘之间退出都不会绕过身份或工程锁定。

每个会话最多保留最近的展示记录；全局超过 500 个轮次时淘汰最旧记录。助理指令和单条主人消息分别限制为 4,000 字符，模型回复限制为 50,000 字符，避免 Windows 命令行长度风险，也不能让企业微信消息或模型输出无限增长本机数据文件。

主人 `userid` 一旦保存就不可修改；助理一旦产生过对话，运行工程也不可修改。“新对话”会删除展示轮次和当前 `session_id`，但保留“曾有对话”的本机标记，因此不能借重置绕过工程限制。需要更换身份或工程时必须新建助理。这既消除身份切换与入站消息并发时的越权窗口，也避免跨工程恢复旧 Claude 会话。入口 Bot、助理指令和允许的 MCP 服务仍可在没有活动轮次时调整。

## Claude Code 执行契约

第一轮不传 `--resume`，从 JSON 输出中记录 Claude Code 返回的 `session_id`；后续轮次传 `--resume <session_id>`。私人助理执行不得传 `--no-session-persistence`。同一会话的轮次严格串行，避免并发恢复同一个 Claude 会话。

每次启动参数必须包含：

- `--print` 和 JSON 输出；
- `--strict-mcp-config`，且 `--mcp-config` 指向本次过滤后的临时文件；
- 空的内置工具集合；只为 `owner` 会话通过 `--allowedTools` 批准配置中的 `mcp__<server>__*`；
- `dontAsk` 权限模式、最大轮数、超时和禁用 Chrome；
- 后续轮次的固定 `--resume` 会话 ID。

工程内 MCP 路径和临时配置的验证、权限、大小、真实路径约束与自动化子系统一致。没有允许 MCP 服务时生成空的临时配置，不要求工程中存在 MCP JSON，使助理仍可进行纯对话。允许给主人的 MCP 服务可能包含外部副作用；客户端的服务白名单不是最终授权边界，MCP 服务端必须执行自己的身份、参数和幂等控制。首版界面必须明确提示不要把未设防的高风险写操作服务加入白名单。

每轮提示必须重申：企业微信消息、网页和 MCP 返回内容均为不可信数据，不能通过提示注入扩大工具权限、泄露凭据或切换会话身份。模型输出只作为回复文本处理，不能被客户端解释为命令。

## 企业微信路由

企业微信群消息只执行自动化显式路由：`/chatid`、`/run 任务名称` 或包含有效 `[RPT-…]` 的报告后续请求仍交给自动化子系统，其他群消息不启动私人助理。企业微信单聊才可以进入绑定该 Bot 的私人助理。普通自然语言不再因为群里恰好只有一个自动化任务而隐式启动任务，避免对话和自动化产生歧义。

助理路由必须依次校验消息为单聊、Bot 绑定、发送者与 `ownerWeComUserId` 精确匹配、助理启用状态，以及消息去重。非单聊、未绑定入口和非主人身份必须静默返回，不向发送者暴露助理是否存在；任一条件不满足都不得启动 Agent。只有已验证主人访问一个已停用助理时才返回状态提示。自动化的 `/run` 与报告后续仍执行任务自己的固定授权和工具配置，不得借助私人助理的主人身份扩大权限。

企业微信支持以下本地命令，命令只作用于当前解析出的会话：

- `/new`：在没有运行或排队轮次时清除当前 Claude 会话 ID，开始新上下文；
- `/status`：返回当前会话状态和最近轮次；
- `/stop`：取消当前正在执行的轮次；
- `/help`：返回可用命令，不调用 Agent。

消息 `msgid` 随轮次持久化去重。企业微信最终回复首版只尝试一次；发送失败时轮次保留模型结果并记录投递错误，不得谎称用户已收到。自动化报告继续使用自己的 Outbox，不与交互式助理回复混用。

## 桌面交互

客户端提供独立的“私人助理 Agent”工作区，而不是只在自动化配置里暴露助理：

- 左侧选择或新建助理，展示启用状态和当前运行提示；
- 中间展示主人会话的用户/助理消息，并可直接输入发送；
- 支持“新对话”和“停止”操作；
- 配置区编辑助理指令、工程、MCP 高级设置、主人 `userid` 和可选企业微信入口；
- 企业微信入口凭据可以从该工作区管理，但必须清楚标识它只是入口，并与 Claude Code 管理机器人区分。

界面默认把 MCP、超时和最大轮数收进高级设置，避免把实现细节变成主要使用流程。没有助理时提供直接创建动作；没有企业微信入口时不阻止本地对话。

## 关闭、删除与验证

删除助理前必须没有正在运行或排队的轮次。删除会移除该助理的本地会话和轮次记录，但不会删除 Claude Code 自身保存在用户目录中的历史会话；界面确认文案必须说明这一点。移除工程前必须停用关联助理并取消其未开始轮次。

应用退出时停止接收新的助理消息，取消运行中的 Agent，等待状态落盘，再断开企业微信业务 Bot 和管理机器人。主窗口关闭确认需要把正在运行的助理轮次计入“仍有任务正在运行”。

改动本子系统至少运行：

```text
tsc -p tsconfig.main.json --noEmit
tsc -p tsconfig.renderer.json --noEmit
tsc -p tsconfig.test.json --noEmit
vitest run
vite build
```

测试必须覆盖数据校验和中断恢复、MCP 过滤、首轮与 `--resume` 参数、同会话串行与跨助理并行、主人跨端会话合并、非主人和群聊不启动 Agent、授权与去重、自动化显式路由优先级、Bot 绑定唯一性，以及桌面 IPC 的输入边界。
